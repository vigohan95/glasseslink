# 后台行为：iOS 到底允许什么

这份文件回答一个问题：**锁屏/切到别的 App 之后，我们的客户端还能做什么。**

先说结论：
- **能**：被 GATT 通知唤醒、短暂处理、重新建立链路；
- **不能**：像前台一样持续跑、持续收 L2CAP 流；
- **不需要**：苹果的配件认证（iAP2 / MFi）。音频类配件走标准蓝牙协议，不需要它。

## 1. 三个机制，别混在一起

| 机制 | 触发条件 | 你得到什么 | 限制 |
| --- | --- | --- | --- |
| `bluetooth-central` 后台模式 | Info.plist 声明；用户授权蓝牙 | App 被挂起后，**外设的连接/断开、特征值通知**会唤醒 App | 每次唤醒只有约 10 秒（可用 `beginBackgroundTask` 延到约 30 秒），不是常驻 |
| 状态恢复 `CBCentralManagerOptionRestoreIdentifierKey` | 系统重启/内存回收后 | App 在后台被重新拉起，`centralManager(_:willRestoreState:)` 里拿回外设与特征 | 只是"重新拉起"，同样受时间限制 |
| L2CAP 通道数据 | —— | **没有任何唤醒语义** | 挂起期间到达的字节不会叫醒 App；恢复前台后可能已经超时或断开 |

关键差别就在这里：**GATT 通知会叫醒你，L2CAP 流不会。**

## 2. 我们的客户端为什么后台会停

我们的数据面走的是 L2CAP CoC（相册、取景、设置都在上面）。这条通道：

- 前台时最快（蓝牙约 120–165 KB/s）；
- 一旦 App 挂起，**没有机制把它唤醒**，于是传输停在半路；
- 唤醒后需要重新 `openL2CAPChannel`，并且要处理"上一个通道还被占着"（会报 already connected，需退避 5–30 秒）。

所以"锁屏后导入会停"是结构性的，不是权限问题，也不是买不买开发者账号的问题。

## 3. 想验证，10 分钟三步

1. **看眼镜有没有可通知的特征**
   在 App 里连接后枚举 `0000fd5f-…` 服务的所有特征，打印 `properties`（是否含 `.notify` / `.indicate`）。
   若有：说明眼镜愿意主动发通知，后台唤醒可行。
2. **做一次后台唤醒实验**
   订阅该特征 → 锁屏 → 让眼镜产生一次事件（按一下拍摄键最省事）→ 解锁看日志里有没有"后台唤醒"时间戳。
3. **测可用时间**
   在 `willRestoreState` / 通知回调里启动 `UIApplication.shared.beginBackgroundTask`，记录被系统强制结束的时刻，得到本机真实预算（通常 10–30 秒）。

## 4. 结论表

| 功能 | 前台 | 锁屏后 |
| --- | --- | --- |
| 拍照（按眼镜快门） | 可以 | 眼镜自己拍，**不需要** App；回到前台再导入 |
| 导入照片/视频 | 可以 | 停；或被通知唤醒后跑一小段（<30 秒），大文件跑不完 |
| 取景（Live） | 可以 | 停（需要持续收流） |
| 改设置 | 可以 | 唤醒窗口内可做（几帧就够） |
| 助手问答 | 可以 | 唤醒窗口内可做一轮，长回答容易断 |
| 自动重连 | 可以 | 可以（连接事件本身会唤醒） |

因此产品设计上应该是：**前台做重活，后台只做"轻动作 + 记忆状态 + 下次接上继续"**。
导入这块正确的做法是断点续传：记录每个素材已收字节与 adler32，下次唤醒/回前台从游标继续（协议本身支持游标，见 `10-media-pipeline.md`）。

## 5. 为什么这不是 MFi 的事

苹果的配件认证（MFi / iAP2）需要：

1. 加入 MFi 计划的**企业资格**与合同；
2. 配件里放苹果签发的**认证芯片**（2.0C 之类）；
3. 规范在 **NDA** 下，只给会员；
4. **配件侧**必须声明并实现 iAP 会话。

也就是说，即使拿到规范，也要改眼镜那一端——那不是客户端能做的事。
更重要的是：**音频类配件（耳机、眼镜的音频）走标准 A2DP/HFP，本来就不需要 MFi。** 苹果不因为"用了 MFi"就给 App 更多后台时间；后台预算由系统按 App 类型统一给。

所以"付费账号有额外后台权限"是误解，实际差异只有：证书有效期、设备数量、TestFlight/上架资格。

## 6. 如果一定要"后台连续传输"，可行与不可行

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| 通知唤醒 + 断点续传 | ✅ | 唯一合规路径；用户感知是"过一会儿自己导完了" |
| 保持前台（引导用户别锁屏） | ✅ | 最简单，配 `isIdleTimerDisabled` 防自动锁屏 |
| 让眼镜把内容推到手机上（服务端推送） | ❌ | 眼镜没有联网通道 |
| 走 Wi-Fi 直连 | ⚠️ | 速率高，但同样受"挂起不唤醒"限制 |
| 用定位/音频等其它后台模式"续命" | ❌ | 审核会拒，且系统仍会挂起 |
| iAP2 配件通道 | ❌ | 需改配件 + 苹果授权，与客户端无关 |

## 7. 给协作模型的说法

如果要让模型帮你实现"通知唤醒 + 断点续传"，用这段：

> 我在写一个 iOS 客户端连我自己的蓝牙眼镜（SwiftUI + CoreBluetooth，已开 bluetooth-central 后台模式与状态恢复）。
> 我需要：①订阅某特征的 notify 并在被唤醒时启动一个短任务；②用 beginBackgroundTask 记录真实预算；
> ③把一个大文件传输改成断点续传（协议支持游标：我发我的已收字节数，对端从那里继续）。
> 请给出实现骨架，并指出哪些 API 在挂起状态下不可用。
